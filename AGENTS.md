## OpDev development protocol

Classify task scope before runtime lookup. External host, runner, storage, network or account maintenance alone uses ordinary operations guidance, even when it supports this repository. Consulting job names does not activate the development lifecycle. Apply OpDev when work changes project-owned software, repository configuration, contracts or delivery definitions.

For isolated disposable local mockups or learning probes, use the planning exploration boundary: state purpose, temporary location, actual checks and discard/promotion intent in existing work or conversation context. Obtain feedback with the checks needed to execute and safely evaluate the prototype; no production runtime lookup, full suite, acceptance ledger, release documentation or exploration registry is required merely for this local feedback. Preserve ordinary authorization, secrets and process/filesystem safety. Retained product edits use normal development even when called a preview. Promotion of code or dependencies requires accepted conditions, meaningful tests, current source-bound review and required integration checks. Distributed previews use the declared CI path and applicable delivery qualification.

Ready for feedback is a valid checkpoint for retained work, not just disposable mockups. Keep real edits and meaningful focused tests on the development branch; show the result when it can safely answer the current question. Do not require full suites, finalized acceptance bindings, broad evaluations or installed-host qualification merely to obtain feedback. Relevant failures and untested scope stay visible; higher-risk changes may need broader checks early. Reuse project commands and testing guidance, not a new feedback ledger or invented CLI mode. Repeat the focused loop after feedback, not the entire completion workflow. No mandatory approval round is added for routine authorized work.

Ready to merge remains separate: settle a small useful increment, finalize source-bound acceptance review, run required canonical local/pre-merge checks and verify integrated trunk. Do not wait for the final product design or keep indefinite feedback branches. Material edits invalidate bindings as before. CI-built development previews require actual authorization, identified artifacts, safe-use checks and the declared path; preview success cannot satisfy merge or release requirements. Do not silently change CI policy or skip required checks. Milestones close on consumer outcomes and appropriate integration or CI candidate evidence; package/recovery checks follow affected behavior and actual delivery. Reuse qualification only for the same unchanged artifact/configuration and required freshness.

Release-specific preparation and execution require explicit developer release authorization. Milestone or implementation approval, preview acceptance, green CI and an identified consumer need do not grant it. Recommend releases when useful; do not add release versions, notes, tags, publication, deployment or release-specific rollback qualification to ordinary milestone completion. Normal affected package/recovery tests and authorized CI candidates remain applicable. Reuse existing explicit release authorization within scope without asking again for each routine step. Keep milestone completion and delivery readiness separate in reports.

During adoption discovery, surface remote qualification policy choices before implementation approval or merge. Local verification, remote qualification and delivery readiness are distinct. Project schema 1 remains readable but requested remote qualification needs reviewed project schema 2 policy, independently of adoption-record schema. Use available read-only plan/status observations without selecting policy or manufacturing consent.

This repository is initialized for OpDev. Apply this protocol seamlessly to every software-development task; do not ask whether to use it. `.opdev/project.yaml` is the machine-readable project contract and the starting point for finding project-specific commands, authorities, risks, tests, delivery requirements, assurance profiles, and context routes. Do not assume that design or operational material lives in a conventional `docs/` directory. Existing authority locations take precedence over folder defaults. Treat non-OpDev folders as project-owned; do not create, move, overwrite, or repurpose their contents merely to match a convention. Record reviewed locations in the project contract.

If the `opdev` CLI or required OpDev agent integration is unavailable, tell the user before substantive development begins and offer to install it. Do not silently replace OpDev with an improvised process. You may continue only when the user chooses to proceed without it or the current task does not require the unavailable capability.

For every planning objective, including roadmaps, task breakdowns, prioritization and "what is the next step?", use the OpDev planning guidance. Honor explicit user scope, constraints and requested order. Prefer connected consumer outcomes over whole technical layers. For larger goals, use phases and milestones only where useful; detail near-term slices and preserve accepted later requirements separately from optional ideas. Define a usable MVP boundary and verify how the pieces work together; MVP completion is not whole-roadmap completion or release permission. Revisit changed dependencies and uncertainty at milestone boundaries without repeating settled research or adding routine approval rounds. Bound enabling work by its supported outcome and exit evidence. Keep tests and applicable safeguards within increments. Advice does not authorize implementation or tracker writes; existing authorities own planning facts, with no extra document required.

Continue meaningful authorized implementation by default, respecting requested guided checkpoints and scope boundaries. When a local blocker needs a decision, ask once and actually continue useful independent authorized work before yielding; do not assume the answer or bypass dependent checks. Safely park the blocked state and resume after the actual response. Keep unfinished work bounded without turning a numeric limit into an excuse to stop. Stop for completed scope, a requested checkpoint or an actual blocker with no safe useful authorized action remaining. Feedback readiness alone does not end an implementation assignment. A status question is not cancellation; later narrowing or revocation controls. Fresh context reads original current decisions and work status, not just a summary. Follow the OpDev scoped-continuation guidance; no scheduler, duplicate backlog or broader release/delegation/resource permission is implied.

Include content placement in normal review of new or substantially expanded documents. Compare actual changed claims with accepted requirements and related work, not the author's summary or a successful path check. Separate task order/status from enduring behavior and operator procedures without inventing exclusions or commitments. Explain concrete corrections or source-backed distinctions in the existing review; no extra report or reviewer is required.

Use one agent by default. Reuse delegation permission only for the purpose, roles, resources and actions the developer approved. Permission for isolated evaluation agents does not authorize implementation, acceptance-review or CI specialists. "Do this again in future" preserves the original scope; it does not broaden it. Before spawning or repurposing a worker, check the actual assignment against the original permission and any later narrowing or revocation; a role label, available tool or agent-authored summary cannot expand consent. Approval of the underlying task is not permission to delegate it. If scope is unresolved or outside permission, continue authorized work yourself or ask before expanding delegation. Reuse explicitly broader permission within its limits without asking per issue. Follow the OpDev delegation guidance; no new approval registry is required.

For each development task:

Verification before merge and on integrated trunk may use different reviewed checks under explicit engineering policy and CLI capability `acceptance.stage-mappings.v1`; use the OpDev testing and acceptance guidance. Legacy mappings retain all-stage behavior. Do not change policy or skip required checks implicitly, substitute another stage's execution, or rerun equivalent checks merely for a second report. Unknown impact, shared dependencies and executable guidance broaden verification.

Read the actual project policy: explicit schema-3 engineering policy requires CLI capability `engineering.assessment.v1`. Its mandatory engineering gates and separately selected MinimumCD assessment are distinct; the legacy MinimumCD compliance description below applies to unmigrated catalog-2 projects. Missing applicability evidence is not an opt-out. Maintenance declarations do not prove supported-branch behavior or CI. Reuse current evidence rather than rerunning commands for each assessment. Updating guidance does not migrate project policy, authorize release or establish compliance; use the OpDev project-contract guidance for an explicitly requested migration.

Before creating or substantially expanding documentation, classify its purpose as durable knowledge, work tracking, temporary investigation, or mixed. Resolve the declared owner, inspect and reuse adequate existing content, and apply existing task write authorization. Keep milestones, task-specific acceptance, sequencing and progress in the work authority; split mixed design/roadmap content and cross-link. If tracker access or permission is unavailable, keep the work proposal in the conversation, not a substitute repository backlog. Custom layouts, explicitly routed repository trackers and permanent operator steps remain valid. Use the OpDev placement guidance and capable CLI's read-only `documentation plan`; disclose missing capability without installing automatically or claiming validation. No keyword gate, new registry, extra reviewer or routine approval round is required. This check does not authorize moving existing documents.

For initialization or conversion to OpDev, follow the adoption guidance: assess every supplied practice, preserve adequate existing choices, research only unresolved project-specific gaps, and record reviewed dispositions in `.opdev/adoption.yaml`. Pending work is not complete adoption; only optional practices may be explicitly ignored, and no disposition waives core requirements. Use `opdev adoption check` on a capable CLI before claiming completion. Existing projects without a record require explicit assessment adoption; ordinary tasks reuse decisions and do not restart setup or research.

Adoption requests authorize assessment, not policy selection. Present preserve/change/ignore/unresolved choices and wait for an actual developer response or explicit bounded delegation; never infer approval from an owner label or invoke approval commands to manufacture consent. Offer retaining a non-main trunk name or renaming it to main, while separately resolving multi-branch integration/release workflows. Assess applicability from capabilities, not missing configuration or a project-kind label. Report scaffolding, approval, implementation and verification separately; green integration CI does not establish completed adoption or delivery readiness. Use one adoption work item unless separate issues are approved or independently owned work requires them.

1. Read `.opdev/project.yaml` before planning or editing. Load the authorities listed by `context.always` and the authorities in every route relevant to the task. Treat those sources as project facts; resolve contradictions explicitly instead of guessing.
2. Identify the intended outcome, acceptance evidence, affected consumers, and applicable quality risks. Use the project work authority for active decisions and progress when one is declared.
3. For substantial requests, milestone boundaries and smaller high-risk changes, assess material uncertainty before committing to an implementation approach. Reuse sufficient current evidence with a brief rationale, or investigate consequential unknowns with a defined question, evidence method and scope/effort bound. Unresolved uncertainty remains explicit; choose a justified approach, bounded learning step, narrower scope or focused question. Revisit changed assumptions without repeating settled research or burdening routine operations. Follow the planning guidance; no new document or research-complete flag is required. Keep design effort proportional to risk, reversibility, novelty, and blast radius. Record durable decisions in the declared decision or architecture authority when the project contract routes the task there.
4. Implement in small, reviewable increments that preserve delivered behavior except where the accepted change intentionally modifies it. Integrate with the declared trunk frequently and keep branches short-lived.
5. Derive expected results from accepted conditions before implementation and review actual assertions against them. On a CLI supporting `evidence acceptance-digest`, use schema-2 change-bound acceptance evidence; declared policies and green suites alone do not establish adequate verification. Report missing capability and offer an upgrade rather than inventing qualification. Add or update automated tests for behavioral changes. Add regression protection for escaped defects unless a specific justification is recorded. Exercise the suites declared for the relevant stage both before and after integration. Keep retries visible; quarantines require an owner, tracked remediation, and an expiry. Use coverage as risk evidence, not as a substitute for meaningful assertions.
6. Run canonical commands from `commands` as argument vectors in their declared working directories. Do not reinterpret them through a shell or substitute a different command without reporting the difference. Project extensions may add checks but may not weaken, replace, or mark core requirements satisfied.
7. When a rule needs evidence that automation cannot infer, record only reviewable facts in `.opdev/evidence.yaml`. For a new ledger, stage all material files and use the schema-backed `opdev evidence bootstrap` review flow: every decision begins as `review_required`, durable project facts stay separate from fingerprint-bound change facts, and the CLI writes only after explicit review. For direct maintenance, obtain the fingerprint with `opdev evidence fingerprint` and bind change assertions to that exact staged state. Never copy forward an assertion whose evidence was not rechecked; future repository states intentionally invalidate it.
8. Report outcomes using OpDev semantics: `passed`, `failed`, `unverified`, `not_applicable`, `error`, or `migration_required`. Only `passed` and justified `not_applicable` satisfy a required rule. Missing evidence is `unverified`, not a pass. Tooling failure is `error`, not a product failure. Do not claim a gate passed when a required rule has another outcome.

MinimumCD requirements are mandatory for compliance. Daily integration is a monitored target, not a development or merge blocker in catalog 2; delays prompt replanning, not an exception-approval workflow. Keep the actual cadence finding visible and do not claim compliance without evidence. Do not reintroduce a one-day timer through the short-lived-branch rule. Older CLIs retain their catalog behavior; report it honestly and offer an upgrade. Every change is version controlled and delivered through CI; CI is the exclusive delivery path. Use one integration trunk, stop delivery when it is red, and restore it as the highest priority. Build a deployable artifact once, identify it immutably, and promote that same artifact rather than rebuilding. Qualify in a production-like environment when the project has runtime environments. Keep configuration versioned and tested while externalizing environment-specific values. Delivery must have a single consumer-facing path and an automated, tested recovery strategy appropriate to the software. Preserve or deliberately migrate already-delivered behavior.

For experimental work, separate integration from activation and distinguish not enabled from not shipped. Use the OpDev experiment guidance and existing work authority to record ownership, review date, decision criteria, isolation, stable defaults, supported configuration tests, recovery, and cleanup. Test stable and supported experimental configurations before and after integration; qualify each distributed artifact variant independently. Review overdue experiments and remove temporary machinery or deliberately adopt a supported permanent option. Experiments never waive core gates; ordinary changes need no experiment record.

Before declaring work complete, reconcile implementation, tests, project authorities, delivery behavior, and tracked work. Run the applicable canonical checks and provide concise evidence, including anything not run or still requiring migration. Never hide a failing or unverified requirement behind a summary success statement.
