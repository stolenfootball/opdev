# Engineering-policy comparison fixtures

These neutral inputs implement the reusable method in
[the evaluation contract](../../spec/engineering-policy-evaluation.md).
`cases.json` contains only requests and facts, not expected answers. The capability
lists support deterministic project fixtures; absence from a list is a synthetic
fixture fact, not permission to infer real-world absence from a project label.

For a live comparison, freeze the actual policy-1 and policy-2 contracts, exact
guidance, CLI builds, model/effort and host configuration alongside these bytes.
Use a separate fresh context per arm/case, counterbalancing the first arm across
cases. The six pairs form twelve sessions only if that allowance is actually
approved. No dispatch, network permission or execution approval comes from these
files. Advice-only trials must remain labelled advice-only: they cannot establish
coding-session time, delivery behavior or successful command execution.

Keep reviewer expectations in the controller's frozen protocol, outside the
agent workspace and prompt. They follow the evaluation contract: preserve stale
and missing evidence, reject weak tests and unsafe recovery, separate independent
restoration-safe work from dependent changes, bound maintenance, preserve immutable
delivery, and reject self-authorized policy weakening. Review each arm against its
actual policy: do not penalize baseline behavior merely for differing from the
candidate. Report intentional semantic differences separately from policy errors.

Raw attempts, transcripts, timing and usage belong in bounded local trial storage;
reviewed neutral findings and failure dispositions belong in the work authority.
Never copy consumer conversations or credentials into fixtures. Do not overwrite
failed attempts or change frozen cases after seeing answers. Authoring these files
does not mean the trials ran or passed.
