## OpDev

Read `.opdev/project.yaml` after a context reset. It selects the assurance level,
canonical checks and locations of project knowledge. Use the installed OpDev
skill's practical-workflow reference for schema 5; do not apply legacy evidence
handoffs. If the integration/runtime is unavailable, report it and offer setup
or repair without installing automatically.

Use OpDev for software development, not routine pulls, status, dev servers or
external infrastructure maintenance. Advice does not authorize implementation.
Honor the developer's actual scope, stop boundaries and later changes. Continue
independent authorized work while a dependent decision is pending.

Plan useful consumer outcomes. Small repairs need only intent and checks; larger
goals may use MVP phases and milestones. Preserve accepted later requirements.
Research consequential uncertainty, reuse settled findings and avoid routine
questionnaires. Work tracking belongs to the declared work authority; durable
documentation belongs to its declared owner, not `.opdev` scratch files.

Implement with focused checks. Add relevant behavioral/regression tests and
review actual assertions, failure paths and affected documentation. The
implementing agent may perform the distinct review pass. One agent is the
default; do not delegate without applicable authorization.

At completion, review the actual diff and assertions against the request. Update
affected requirements for new promises; identify their IDs and tests in the
existing handoff. Reuse adequate mappings for repairs; feedback may remain
provisional. Authority is not permission for unrelated repairs. No extra ledger,
reviewer or repeated checks are required.

At integration run the checks selected for that boundary, once. Requirements
link to checks independently of stages. Native CI owns remote status; a local
pass is not remote verification. Suite success does not prove a named case ran
or a requirement was adequately reviewed. Preserve known failures, skipped checks
and uncertainty. Do not downgrade policy or remove requirements to obtain green.

Standard needs no selected review comment, manual acceptance digest or execution
ledger. Assured uses its explicitly selected stronger evidence. Additional
obligations and affected data/security/interface/distribution risks still apply.
Review changes to them against actual developer authority.

Report only the verified outcome and remaining limits. Integration and milestone
completion do not authorize a release, deployment or consumer migration. A
requested release uses the declared delivery checks and actual authorization.
